# How agent-approvals works

## The pieces

| Piece | What it does | Where |
| --- | --- | --- |
| `approvals` command | Agents submit cards, ask questions, post new versions, mark requests done, and read their inbox | In each agent's session |
| Records | One JSON file per request: every version, every reply and question, the decision, the outbox of messages to the agent, and how to reach the agent | `~/.approvals/requests/` on the hub |
| Listener | On the hub: holds the Slack connection, records button presses and replies, enforces deadlines, serves the records to the other machines. On every machine: delivers messages to the agents there | launchd or systemd service, `approvals listen` |
| Skill | Teaches agents when to ask, how to write a card, and what to do with answers | `skills/approvals/` |

**More than one Slack workspace.** Each workspace has its own folder (`~/.approvals` for the main one, `~/.approvals/<name>/` for each other), with its own config, records, request numbers and listener. The code is the same for all of them; only the folder differs. The command picks the folder by itself: a request's number prefix says which workspace it belongs to, and for a new request or the inbox, the agent's working folder decides, by each workspace's `folders` setting. The skill is the same everywhere, so an agent never chooses a workspace and can't choose the wrong one.

**More than one approver in a workspace.** The top-level `approver`, `approver_name` and `channel` remain the default. Optional `approvers` entries, keyed by short name, each supply those same three fields for another person and their channel. `approvals submit --to <name>` saves that name as `target` on every card submitted together; an unknown name is refused with the names available. Every later operation resolves the card's approver from its record: posts, updates, notes, reactions, files, thread reads and replies use that person's channel, and cards and agent messages use their name. The conversation a card came from still uses its own channel. An old record without `target` uses the default. A name missing from config is an error, never a reason to use the default. All channels share the workspace's existing app, hub and Socket Mode connection.

**More than one machine.** Slack hands each button press to only one of the connections an app holds, so a workspace whose agents run on several machines still has one listener connected to Slack: the hub's. A listener per machine with its own records would lose the presses that went to another machine and post the morning list once per machine.
- **The records stay on the hub.** On any other machine, the command and the service read and change them over HTTP (`hub.py`). Each change is made to the copy it read, and when the record changed on the hub in between, the hub refuses it and the change is made again on the new copy. So two machines answering, acknowledging or delivering on one request at the same moment can't undo each other.
- **Each machine posts to Slack itself** with its own copy of the bot token. The hub accepts only callers that sign with a key derived from that token, so no other secret is shared.
- **Each card names the machine it was asked from** (`reach.machine`, from `~/.approvals/machine.json`). That machine's service asks the hub every 10 seconds for the messages due for its sessions, and delivers them as below. A card from before machines had names belongs to the hub, and without a hub every card belongs to the one machine.
- **The machine follows the agent.** Any command the asker runs updates the card's reach, its machine included. A message the named machine can't deliver because the session's transcript isn't there is marked a stray: every machine looks for that session's transcript about once a minute, and the one that has it takes the message and the card's later ones.

**The Slack connection.** A hub whose cards the pod dashboard's record keeps (`record_url`) holds none: the Slack app's Socket Mode is off, its interactivity and events go to the record's own address, and the hub hears each answer from the record's stream of changes (README, "When the record keeps the cards"). Any other hub holds it with Slack's built-in Socket Mode client, which opens a new connection by itself when one dies. That client reads every connection, and answers Slack's pings, on one long-lived thread. When a TLS write fails with a system error such as a broken pipe, Python's `ssl` module leaves that error queued on the thread, and the next read there that has to wait for data reports it again, on whatever connection it's reading. So one ping answered on a dead connection made every later connection fail on its first read. On November 8, 2026 that left the hub reconnecting every 5 seconds for 42 minutes, hearing no button presses, until the service restarted. `listener.SlackConnection` empties that thread's error queue before it reads each connection.

## Reading a card before posting

`approvals read` gives each card to a fresh headless reader with the approver's configured writing rules and knowledge, so the writer can find places that are hard to understand without the writer's context. It prints the reader's observations without posting or saving a request. The reader is not the approver and is not a gate: `submit` neither calls it nor requires it.

## The sender

An agent's Slack posts can carry its team's name and picture. The command looks for `.approvals.json` in its working folder, then each parent, and stops at the first file. Its `post_as` is `{"name": "Design team", "icon_url": "https://example.com/design.png"}`. No file, or no `post_as` in that nearest file, keeps the app's usual sender. A present sender needs a nonempty name of at most 80 characters and an HTTPS picture URL; a malformed one refuses the command before it posts.

Every message a command posts uses that command's sender: cards, versions and their notices, questions, answers, acknowledgements, evidence posted as text, status notes, the reviewer's read and the deputy's line. The reviewer's own folder supplies its sender. At submit the record keeps the asker's sender as `as`, so the service can use it in the conversation the card came from. The service's own notes in the card's thread, including delivery failures and acknowledgement warnings, keep the app's name. Slack file uploads cannot carry a custom sender, so they also keep the app's name.

The workspace's optional `list_as`, in the same shape, supplies the sender for morning lists, lists asked for and the deputy's morning summary. Without it those posts look as before. Custom senders are `username` and `icon_url` on `chat.postMessage`, using the app's token and `chat:write.customize`. Every post still belongs to the approvals app, so Slack keeps sending its button presses to the hub.

## The card and the thread it came from

A card may answer a message in an existing Slack conversation: `approvals submit --thread <message link>`, or `thread` in its JSON. The command's link wins for every card in a set. All links are checked before anything is posted: an HTTPS Slack message link in this workspace, optionally with `thread_ts`. The record's `thread` keeps the link, channel, message timestamp and thread root. The card's own thread in the approvals channel remains `thread_ts`.

At submit the command reads the named message and channel name. A person's words are saved as plain text, with readable mentions and links, shortened to about 300 characters, and marked when they are the approver's. Right under the card's frame line, a small line says which sender and channel the conversation is with and links to it; the saved words sit below, starting with “You:” when they are his. An answered card keeps just the link line. When the card would exceed Slack's 50 blocks, these optional blocks are dropped before any material needed to decide.

After the full card is posted, the conversation gets a small card under the asker's sender. `cards.small_blocks(rec)` always draws the newest version: while it waits, its title, the first editable quote (else the first quote), what a yes covers and its answer buttons. Only a plain yes-or-no card has buttons there, with the full card's values; a pick, rows or batch takes the approver to the full card. After his reply it says the agent is changing it. After a decision or closure it says what happened, by whom and when, and the newest status or done line. Every state ends with the card number and a link to the full card, with the version from the second one on.

The record keeps the small card's timestamp. Every redraw of the full card redraws it too, in its own channel; a failed small-card update is logged and leaves the full card's update standing. A refusal after pressing there answers in the channel and thread of that press. The listener also copies each of the approver's replies on the full card, including words from a pop-up, into the conversation once, under the asker's sender, with his name, the approvals channel and the time above the quote. The record keeps those post timestamps so `purge-tests` can delete them along with the small card.

When the app cannot read the conversation, such as a direct message with another app, the full card keeps its link and no small card is posted. The command tells the agent that the thread will not show the card and to link it there itself. Records without `as` or `thread` behave as before.

## One thread per request

The card is the first post. Everything about the request stays in its thread:
- the agent's evidence, one post per item, with any file it names attached so it opens in Slack;
- the approver's replies, which count as feedback;
- the agent's questions, marked ❓;
- a new version the agent posts on its own, as a full card at the bottom where the approver reads;
- a new version that answers a reply (his or a teammate's), as one post under it: the agent's answer when he asked something (`approvals revise --answer`), then a line saying the card at the top changed, with the `changes` line and a link to the card. A whole card there buried the answer he came back for (Amir, November 22, 2026: "I can't get a giant blob as a response because I can't actually find the answer to my ... question in it"). The post is recorded as the agent's answer or acknowledgement with its Slack id, so the pod dashboard shows it once.

When a version is replaced:
- the first post turns into the newest version, so it can be approved from the channel;
- the old version is never posted again, and an earlier copy of it in the thread shrinks to one line with a See button, so the thread holds one whole card at a time and what's new is plain. The new card opens with what changed and a See button for the version before it. (Amir, November 10, 2026, when each version re-posted the one before it in full: "I see an accumulating set of copies ... and can't figure out what is new.");
- older versions' buttons stop working;
- a version posted on its own gets a one-line post in the channel saying it is waiting, since the thread may be days old, and the one that announced the version before it is taken down; a version that answers a reply gets none, since he is in the thread, and an older copy's line says the new version is at the top. Questions are sent to the channel the same way.

Slack drops buttons from a thread reply that is also sent to the channel. That's why the first post carries the newest version, and the channel gets a line pointing to it rather than the card.

A decision belongs to the version it was made on. A new version after a yes reopens the request with working buttons, and the record keeps the yes on the old version. A declined request takes no new versions; a different proposal is a new card. A question the agent asks on an approved card (`approvals ask`) leaves it `revising` once he answers, since the answer may change what the yes covers. When it doesn't ("sure, schedule it whenever" after the agent asked which hour to use once the approved one passed), the agent records the answer with `approvals record --approved`, which stands as his new decision on the same version, and `done` works again; a second button press on that version still counts once. On a card with rows whose rows were all decided, the same record (for the card, or for one row with `--part`) settles the card from its rows again. An answer asking for a change gets a new version.

An agent that no longer stands behind a card runs `approvals withdraw`: the card shows "Withdrawn" with its reason, the buttons go away, and a press says the agent withdrew it.

When the approver decides:
- the card shows ✅ or ❌ with their name and the time, and the buttons go away;
- the agent adds "Done" and what it checked when it finishes.

## The card's shape, and its answers

A card's `type` says what the action is; its fields say how the approver judges it and answers it. The renderer is `cards.py`; what an answer does to the record is `core.py`.

**The layout** follows how the approver reads, cold and on a phone (Amir, November 10, 2026: "It's just a bunch of text all jammed together"). Top to bottom: the action as the title; one small line with what it belongs to and who sent it; the required `why` line, what the business gets and why now; the version note; the picture; a divider; each fact as its own block with its label above it, and lines starting "- " drawn as bullets; quotes, tables, options and rows; a divider; what a yes covers and doesn't, at full size; the link buttons and the answer buttons; and one small line with the card number, its version, the deadline and what no answer means. A card that would pass Slack's 50 blocks that way draws its facts in one block instead. Cards from before the why line draw without one.

One card is answered one way:

- **A yes or no**, as before, with buttons named for what happens. `change_label` adds a Change button; quotes marked `edit` add Edit the words.
- **A pick** among `options`. With pictures, the options are carousel cards side by side, each with its own button and the sender's pick marked; without, they're buttons, with any option's `title` drawn above them. An option's `name` is its button, so it says what a tap does, and a name that is only a key ("A", "Option 2") is refused. The decision records the `choice`.
- **A row each** (`parts`): each row has its own buttons and its own answer, kept in `answers` by the row's id (its `id`, else its position). The card is waiting on the approver while any row is open, back with the agent while a row waits for a new version (Change on that row), and otherwise approved if any row was approved or chosen, declined if none was. Approve all answers every open plain row except those marked `own_yes`, in one message. At the deadline only the open rows close. A row's own `quotes` (their message, the reply) are drawn under its title, right above its buttons; a Read-button quote is refused on a card with rows, because it sent the approver to the bottom of the card and back for each row (November 11, 2026: "I would rather get separate approval cards than have this weird homework").
- **A batch** (`items`): a yes covers all; Pick which opens a checklist, and the decision records which `items` were approved.

Everything else (the frame line `part_of`, `if_no_answer`, `journey`, `gallery`, `sections`, `links`, `from`) can go on any card.

**What a card decides** (`about`): where the pod dashboard's record keeps the cards, a card may name the one thing in the record it decides, by its id (`X-346`, `F-21`, `POD-4`). It goes with the version like any other field, and the record checks it: a card naming a thing the record doesn't hold, or an experiment or a feature another open card already asks about (for those a second open card can only be the same ask again; any other thing may have several), is refused, and the refusal reaches the agent in the record's own words on whatever machine it submitted from. The approver's answer on that version lands as his decision on that thing. A later version keeps the thing the card named: one that names nothing stays on it, and one that names another thing is refused, since a card about something else is a new card. A new card that names nothing still goes up: `approvals submit` says so to the asker as it posts, and the record asks the asker (`pd mine`) until it ties the card to the thing its yes decided with `pd tie <id> <card>`, so nothing stops a card from reaching the approver for want of an id.

**Whom it went to** (`recipients`): an `email` or `reply` card says whom it goes to as a field of its own, one `{"place", "handle"}` each, the handle exactly as the place writes it, beside `about`. Submit refuses one without it, a place not on the tool's list (`cards.RECIPIENT_PLACES`), or a handle not of its place's shape, and each refusal says what that place's handle is, so the asker fixes the card in one more try; the card shows it under From, and a new version keeps it. The place says what the handle is: an address for `email`, a handle for the social places, a web address for `contact form` (a site with no address), `support ticket` (a provider's own desk) and `forum`; for a player, an id, never their address: `email thread` (one who wrote to us by email), `player account` (one who didn't: their account's id in our app), `google play review`, `app store review`, or whose note for `testers' feedback`; who in a few words for `mailing`. `other` is the one stated place for what no listed place fits: its handle says where and whom in a few words with no address, it matches no route, and the record counts the cards that use it, so a place that keeps appearing there is added to the list by a person, never guessed. The list was read against every email and reply card of the 30 days to November 22, 2026, 253 of them, and takes each (pod-dashboard `design/notes/card-recipient-2.md`). The record gets it with the card and, when the card is done, moves the person whose route equals a recipient's handle (letters' case and a leading @ aside), and asks the asker about one that matches nobody. A card put up before the field (November 22, 2026) has none: nothing reads it from the card's facts, From line or done line.

**Corrections that come with the form** (`corrections_seen`): where the record keeps the cards, it also keeps up to four open corrections for each card type, each written by an agent from an earlier card's retro. `approvals guide <type>` prints a type's open corrections whole, each with the line he gave it in on a card where there is one, then the `corrections_seen` line naming them and that type's section of the skill's `references/cards.md`; the skill sends an agent there before it drafts, so the corrections reach it before the judgment they were written for, and if the record can't be read it says so and still prints the section. `approvals read` and `approvals submit` read them from the record (through the hub on any other machine) and print, whole, those of a card's type whenever the card's `corrections_seen` doesn't name every one of them by id; `read` reads them before starting the reader. `submit` sends the ids the card names with the card, off the card itself, and names the agent that put it up on the version (`actor`, its Herdr name), so the record keeps that this agent was shown each one on this card. Once the record's rule is on, it refuses a new card that doesn't name them all, printing them whole; until then the card goes up and `submit` prints them after its number.

**A user journey** compares today with the change for up to four kinds of user. An entry lays out ordered steps with the action between screens, or pairs of screens that compare the change in different places. It shows what happens today, including where a path ends, and at least one screen with the change. A journey meets a card type's media requirement, and its maps and page button count toward Slack's block limit. The cold reader gets the words of each path and action in journey order.

**A set** is several cards sent in one `approvals submit a.json b.json`, for things that belong together but each need their own reading. Each is its own record, thread, deadline and answer; the record keeps `set: {"n", "of"}`, and the frame line and the notification line show "2 of 4". All are validated before any is posted, so a set never goes out half.

**Each answer reaches the agent as its own message, naming exactly what it answers:** a row's answer names the row by number and title and says where the other rows stand ("This answer is for part 2 only; part 1 is approved, parts 3 and 4 are waiting"); a pick names the option; a batch lists what to do and what to leave out; edited words are quoted as a JSON string, so the line breaks survive the one-line message.

**Buttons.** Each button's value is `<id>|<version>|<what>`, as before: `approve` and `decline` mean what they always did, so cards already in the channel keep working. The new ones are `pick:<i>`, `all`, `p<j>:approve|decline|pick:<i>`, `offer:stop|keep`, `takeback` (Take it back, on an auto-approved card), and the ones that open a pop-up: `change`, `p<j>:change`, `edit`, `items`, `read:<quote>`, `pic:<picture>` and `see`.

**Pop-ups.** Slack allows 3 seconds from a press to open a pop-up, so the hub opens it right after acknowledging the press, after checking the card hasn't moved on (a newer version, an answered row). It checks the version and who can answer again on submission, and shows refusals inside the box. A change from a pop-up is posted in the thread too, so the thread keeps the whole record. Anyone can open Read and See the card, and Full size and See it are links anyone can follow.

**Pictures.** Slack shows a picture inside a carousel card only once the file is shared where the card is; a privately uploaded file shows as a broken image there, though it works in an image block. So a new card is posted, its pictures are posted in its thread in one message (full size, which is also where they open), and the card is redrawn with them. Slack also crops a carousel card's picture to a fixed landscape frame, which cuts a phone screenshot down to its middle, so each carousel picture is first fitted to that frame (`pictures.card_frame`): zoomed onto what changed and outlined when it has a `mark`, otherwise whole and letterboxed. Every picture is also posted whole, at its own resolution, and a slide's Full size and a row's See it are links to that post, so it opens in Slack's own viewer at full resolution with zoom; a pop-up would shrink it to the pop-up's width, about 500 pixels, where a slide or a phone screen can't be read. A row's thumbnail is a section accessory, which Slack doesn't let anyone tap. Cards from before this change have no links and still open the picture in a pop-up.

A journey puts all its maps first in the thread's picture post, then its full-size screens in entry and step order, today before after. A repeated file is uploaded once. Gallery, row and option pictures follow. The open card and the **See the card** pop-up show the maps above the gallery. Once the record has its Slack link, the configured `page_share_command` can publish the version's static page before the pictures are posted. The version keeps that URL as `journey_url` for its **See it big** button and keeps the page's entries and image filenames as `journey_data`. The page links back to Slack and opens the screens side by side in the full-screen viewer.

**Related cards.** The hub groups by the record's `frame` or the latest version's `part_of`, ignoring case and whitespace differences. It builds one page per name, target channel and TEST flag when at least two cards qualify. A card qualifies when it is posted, has a published journey with picture references, and the morning list counts it as waiting or its decision is at most seven days old. The page shows the newest 20 settled cards and counts any additional settled cards inside that window. Withdrawn cards are excluded. Cards still waiting without a published journey appear as links below the screens. Both pages use the same journey template and viewer, and the group uses the images already published with each version.

The hub's sweep saves each page's random slug, current address and content fingerprint in `groups.json`. When the content changes, it republishes with `page_slug_flag` and the saved slug if configured. It tries failed publications again on the next sweep. A record's `group` field drives its **All … in …** button. The sweep redraws cards when that field changes or is cleared. Changing `--part-of` updates the old and new groups on the next sweep. `approvals names` and the name suggestions for `read` and `submit` use summaries computed where the records are kept.

**Revisions.** A new version keeps the answer of each row the agent left exactly as it was, and asks again about every row it changed, plus rows that closed with no answer. The changed row is marked new, and the line in the channel carries the version's `changes`.

**Keeping a posted card true.** `approvals status` adds a line to a card (what happened, what comes next, a condition waiting on the approver, the other side's reply to a message sent as him), sets the answered card's headline, or sets the frame line. Each redraws the card in place, so it notifies no one and leaves answers and buttons as they were. A condition waiting on the approver is also posted in the thread and keeps the card on the morning list until the agent's next line. An answered card collapses to its timeline, with a button that opens the card as it was asked.

## Who counts

- **Buttons and pop-ups.** The card's configured approver can answer. The current teammate can also answer once the deputy's send is delivered or as soon as the approver hands over the card. With `team_answers_any` on, the default approver and every member of `team` can answer any card. A refusal names the approver, including when a button is pressed in the conversation the card came from.
- **Thread replies.** The same people can reply in the card's channel thread. The hub also polls the recipient's replies in the direct message. The listener hears events from every configured approver's channel and ignores channels it doesn't serve. The agent's own posts in the thread never count. Only the channel's approver can ask for a fresh list by posting there.
- **Elsewhere:** a yes given outside Slack counts once an agent records it with `approvals record`, quoting the approver's words.
- **After a decision:** a reply on an approved, declined, done or withdrawn card still goes to the agent, as a reply after the decision.
- **Order of saving:** a button press is saved together with the message to the agent before Slack is told the press was received. Stamping the card comes after and is retried on its own, so a failed card update can't lose a decision.

## Getting an answer to the agent

Every request records how to reach the agent that asked. The `approvals` command reads this from the agent's own environment on every call:
- runtime: Claude Code `CLAUDE_CODE_SESSION_ID`, Codex `CODEX_THREAD_ID` or Antigravity `ANTIGRAVITY_CONVERSATION_ID`;
- working folder and machine;
- Herdr session, workspace and pane.

`approvals submit` refuses a card when its shell has neither session id, since nothing could ever be typed back to it. That happened when two pods on other machines posted their cards over ssh to the Mac (November 7 and 8, 2026): 18 cards were saved with no asker, and every answer waited in an inbox.

When there's a message for the agent, the listener:

1. **Checks it isn't already there.** If the session's transcript already holds the message's reference code, it marks the message delivered and stops. That covers a restart between sending and recording.
2. **Finds where the asker is running.**
   - It checks the recorded pane first, then every pane on the machine.
   - **Claude:** each process writes the session id it's running to `<config dir>/sessions/<pid>.json`.
   - **Codex:** the session id is read from the session file the process holds open (skipping subagent rollouts).
   - **Antigravity:** the conversation id is read from the presence lock or conversation database the process holds open.
   - **A different session counts as the asker only if it's a moved copy or a continuation.** A moved copy is the asker after AI Manager moved it to another account: it starts with the same first prompt and first reply (AI Manager rewrites session ids inside the text, so ids are ignored in the comparison) and has the request number in its history. A continuation carries the asker's work into a new session, as AI Manager does when an account hits its usage limit: it opens with Claude's summary, which names the transcript it continues, so the chain can be followed back. A later run of the same scheduled agent, another agent in the same folder, or a sub-agent may start the same way, but continues nothing and made none of this request.
   - **A session stopped at its usage limit can't take an answer.** Its last reply is Claude's "You've hit your ... limit" notice, or its screen shows the usage-limit menu. The service looks past it to a session continuing its work, and never types into that menu, whose third choice switches the account to paid usage credits.
3. **If the asker is running and can work,** it types the message and presses Enter through Herdr straight away. It never starts a second copy of a session that's already running. If the session runs outside Herdr, the message waits and is retried.
4. **If it isn't running, nothing starts it.** The approver decides when an agent runs: they may have stopped a pod on purpose, and an answer is not an instruction to run. The message waits on the record, and the thread gets one 💤 note saying the agent isn't running and the answer is waiting. When the agent is back, the skill has it run `approvals inbox` before anything else, which hands it every answer that came while it was stopped and marks each 📨. Those answers are never typed in by the service, even once the session is running again: the agent reads them itself. A session that is running but stopped at its usage limit isn't "not running": its answer waits for a session continuing its work, as above.
5. **Confirms delivery, separately.** Once the message is typed, the machine checks the session's transcript every 3 seconds for its reference code, which appears when the agent takes the message in. Then the approver's reply, or the card for a button press, gets 📨. A message not seen within 90 seconds counts as a failure (below).
6. **If delivery fails,** it retries every 5 minutes, then hourly after three failures. It posts one ⚠️ note in the thread saying why. A request asked from outside Claude, Codex or Antigravity gets the message in its `approvals inbox`. A session whose transcript isn't on this machine gets it there too, until a machine that has the transcript takes it (above). A session whose transcript is here is here, whatever name the card gives the machine.

When `alarm` is configured, the hub checks every 30 seconds for answers at least 60 seconds old that failed delivery, can only be picked up from the inbox, or have not been typed at all. It marks each once before posting to the operations channel and waking the tool's owner; stopped agents, decisions held for their turn, and answers typed but awaiting transcript confirmation do not raise alarms.

A request's messages arrive in the order they were sent. A later one is typed right behind the earlier one, as soon as that one is typed, without waiting for it to show up in the transcript. Claude takes typed messages in at its next step, so the agent reads them together: a "wait, don't send" lands with the yes it takes back, and a run of corrections arrives at once. When each waited for the one before to show up, an agent acted on a yes in the 5 seconds before the wait behind it arrived (November 9, 2026). A later message waits only when the earlier one couldn't be typed. One waiting for an agent that wasn't running doesn't hold up the next: an answer that comes once the agent is running again is typed in, and the waiting ones are in its inbox.

**Approvals pressed in a row go one at a time.** Without this, a run of yeses landed within seconds of each other, before the agent had reacted to the first: on November 8, 2026 nine Instagram approvals pressed within 23 seconds were all typed into one agent within 29. Now a decision (a button or a pop-up that decides: approve, decline, a pick, Approve all, a row's answer, Pick which, Edit the words) waits while its agent, the session that asked, has an answer typed in during the last 2 minutes that it hasn't acknowledged. The agent's waiting decisions go oldest first, one at a time, each once the one before is acknowledged, or 2 minutes after it was typed if no acknowledgement comes. Agents usually acknowledge within seconds (half within 10, 9 in 10 within 48, over November 2 to 9). Decisions for different agents don't wait on each other. While a card's decision waits, the card has ⏳, which goes when the decision is released; 📨 still marks it landing. A thread reply, or the words in a Change pop-up, never waits: the approver correcting himself should reach the agent at once, even mid-task. Each reply is its own message. A reply on a card whose decision is waiting releases that decision, and the reply is typed right behind it, so a "wait, don't send" is never held behind the yes it takes back.

**Resuming, for agent-email.** `router.deliver` can still resume a closed session, and agent-email, which imports it, does, so a reply to an email reaches a session that has closed. It finds the newest session that can still work (the newest moved copy or continuation, or the asker, skipping any stopped at its usage limit); reuses the recorded pane if it still exists in the recorded Herdr session and only a shell is in its foreground, otherwise opens a tab in the agent's workspace or a new workspace labeled for the agent if that's gone, starting `default_herdr_session` headless if no Herdr session is running; runs `aim claude resume <id>`, `aim codex resume-fresh <id>` or `agy --conversation <id> --dangerously-skip-permissions`; waits until the pane is ready (closing it if it lands on Claude's usage-limit menu); records the id the resumed session reports; and sends the message. Approvals calls it with `resume=False`.

Only the asker, a moved copy or a continuation of it can change where a request's answers go. A continuation's `approvals inbox` also shows the request's waiting answers. If another session runs a command on the request, that's noted on the record and changes nothing.

A deliberate fork shares its lead's opening and may hold its request numbers, but is a separate asker. Whatever creates it runs `approvals fork <session id>` in the workspace's folder; its family is that first id. When the fork moves or continues, its launcher watches the pane, learns the new id within a minute and runs `approvals fork <new session id> --same-as <earlier session id>`. Registering an id again leaves its family unchanged. `approvals fork` lists one `session family` per line. The registry stays in `forks.json` beside the records on the hub, read and written over HTTP (`/forks`), with reads cached for at most 15 seconds per workspace per process.

Two sessions can count as the same agent only when their families are equal; an unregistered session has no family. This check comes before moved-copy or continuation matching and also applies to earlier ids, inbox claims by agent name, and changes to where answers go (`approvals repoint` included). A registered fork and a session outside its family cannot take, receive or redirect each other's answers. Within a family the existing transcript checks still apply, and two unregistered sessions behave as before. An operator's explicit `inbox --all` is unchanged. `approvals inbox --peek --session <session id>` prints only the number of undelivered answers addressed to that recorded id, including eligible earlier ids and reviewer or deputy messages. The hub counts them in one call without handing any out, so an idle fork's launcher can check before closing it.

**A session started again with none of the old one's history takes over by `approvals repoint <old> <new>`.** A pod restored from a save starts each member in a fresh session whose first message names the saved session; it holds none of that session's history, so it is neither a moved copy nor a continuation, and before this command an answer to the saved session's cards reached nobody (November 8, 2026, in three pods; two leads re-pointed their cards by hand). So whatever restarts the agent, knowing which old session each new one replaces, runs the command on the machine where the new one runs: every open request whose answers go to the old session then goes to the new one (its pane, folder and machine read from the running session), the old id joins `earlier_ids`, and the record notes `taken_over`. It refuses when the new session isn't running on that machine or the old one still is, and changes nothing. It moves nothing between a registered fork and a session outside its family. Answers that waited while the agent was stopped stay in its `approvals inbox`, which now counts it as the asker. psbrain's `./pod restore` runs it for each restored member, with agent-email's `agent-email repoint`, so no member has a step to remember.

**An answer finds the agent even when nothing re-pointed its cards.** Re-pointing depends on every way an agent gets a new session remembering to do it, and most don't: a member restarted on its own, a pod moved to another machine, a session started by hand. On November 15, 2026, 68 open cards from 34 agents named a session that ran nowhere while the same agent worked on in a new one, and the approver's answer on one was told the agent "isn't running". So when a machine finds the asker's session isn't running, it first asks where the same agent runs now (`core.successor`): the newest other session seen running an approvals command under the same name and runtime since the card last heard from its asker, never across fork families. How far the name is trusted follows who gave it: a name the launcher set (`APPROVALS_FROM`, kept as `named_by_launcher` on the reach) is the member's own from any folder, since members raise cards from their work folders; a name the agent typed counts only from the same folder (compared under the user's home, so `/Users/<name>` and `/home/<name>` match); a name nobody gave is the folder's own and joins nothing, since ten agents had run a command from the repository's root as "psbrain". Where a session was seen comes from the reach on that agent's other cards, and from the `seen` reach now kept on each `used_by_other_session` event. If there is one, every open card of the old session, and the card being answered, is handed to it as `repoint` would (`taken_over`), and the machine that session is on types the answer in on its next pass. If that session isn't running either, the answer waits and the thread gets its 💤 note as before. A session still running keeps its answers: another session of the same name takes nothing while the asker runs.

Every message starts with `[Approvals]` and the request number, quotes the approver's words exactly, and says what to do next. It's sent as one line, so nothing is submitted half-typed.

## Part of

"Part of:" on the Slack card gives the card's `part_of` words and the id of the pod dashboard's thing it decides (`about`, which the record requires of a new card), so the approver sees from the card where his answer will land.


## A reviewer for some types

Amir wants the CFO's read of every request for money in front of him before he answers (November 11, 2026). So one session per workspace can review the cards of some types. `approvals review --types budget,purchase,money` records the session's reach, the way a submit records the asker's, in `reviewer.json` beside the records on the hub, which the other machines read and write over HTTP (`/reviewer`). Running it again from another session moves the role there, with the messages still waiting for it, and so does `approvals repoint`, which a pod restore runs; `approvals review --off` ends it. With no reviewer, nothing changes.

- **What it hears:** a card of its types when it's posted, each new version, and each of the approver's answers (a decision, a row's answer, Approve all, a reply in the thread, a yes recorded from elsewhere), with his words. Each is a message on the card's outbox marked `to: reviewer`, delivered as answers are, by the machine the reviewer's session runs on; a reviewer that isn't running finds them in its `approvals inbox`. They need no acknowledgement, get no 📨, and post nothing in the thread when they can't be delivered, since the approver doesn't wait on them.
- **The asker's side doesn't change.** The asker's messages and the reviewer's are queued apart, so neither waits for the other; the reviewer's never release a decision paced for the asker, and where the reviewer's session is never changes where the asker's answers go. Each `approvals inbox` hands out only its own side's messages.
- **TEST cards** reach only a reviewer set up from a test run (`APPROVALS_TEST=1`), and a real reviewer hears only real cards, so a live test's budget cards never reach the CFO. The reviewer's own cards (the CFO asking to move cash) don't come back to it either.
- **The note:** `approvals note <id> --file read.md`, from the reviewer's own session only, posts its read in the card's thread under the reviewer's name. It changes nothing on the card, and nothing waits on it: the approver may answer before it lands.

## The deputy

Amir answers about 60 cards a day, and most get a plain Approve with no words (November 12, 2026: he asked for an agent that learns which cards he approves every time and approves those for him). So one session per workspace can be the default approver's deputy: it hears every card for that approver and makes its own call on each. Cards for named approvers are excluded from its messages, and it cannot make a deputy call on them; they wait for their own approver. Which default-approver cards to approve is the deputy agent's own judgment, taught in its own instructions; the tool never decides, filters or scores those cards. It carries the call, shows it, sums it up each morning, and lets the approver take it back. ("The approver" is the person; the role is "the deputy". What the approver reads says "auto-approved" and names the agent.)

- **The role** works as the reviewer's does. `approvals deputy --agent <name>` records the session's reach in `deputy.json` beside the records on the hub (`/deputy` over HTTP), with `live` (auto-approval on or not), `test`, `since` and `live_since`. Running it from another session moves the role there and keeps its mode, so a restored session picks up where the old one stood, and `approvals repoint` moves it too. `approvals deputy --live` and `--dry-run` switch the mode from any session, for whoever carries out the approver's word; his own switch is the button on the morning summary. Where the record keeps the cards, it keeps the deputy too: only the approver switches the mode, with that button, and `--live` and `--dry-run` refuse. `--off` ends the role, and with no deputy nothing changes.
- **What it hears,** on the card's outbox marked `to: deputy`, delivered as the reviewer's messages are (by the machine its session is on, no acknowledgement, no 📨, nothing in the thread when it can't be delivered, its `approvals inbox` when it was stopped): each card when it's posted, with the commands to make its call; each new version, with its `changes` line and that a call on the earlier version doesn't carry to it; everything the approver says or does on a card other than a plain yes (a reply in the thread, before or after a decision, a decline, a Remove, a change asked on a row, a yes with his own edited words or with words recorded from elsewhere, a pick, a partial batch, a take-back), with his words quoted exactly; and an agent's withdrawal with its reason. A plain Approve with no words isn't sent: the deputy reads those from the records (`approvals history`). TEST cards reach only a deputy set up from a test run, and the deputy's own cards don't come back to it. The asker's, the reviewer's and the deputy's messages are queued apart and never wait on each other, and each `approvals inbox` hands out only its own side's.
- **The call:** `approvals call <id> --approve|--his --why "<why>"`, from the deputy's own session only. It belongs to the newest version and is kept in `calls` on the record (`version`, `call`, `why`, `by`, `at`, and `live`, the mode at that moment), with a `call` event. It's refused, with nothing recorded and the reason said, when the card is no longer waiting on the approver's first answer for that version (decided, withdrawn or removed, expired, back with its agent after his reply, or already answered on that version by a reply or a row), when that version already has a call (except that a dry-run call can be made again once auto-approval is on, since a dry run approved nothing: the new call stands as that version's call, and the dry-run one stays in the events), and for `--approve` on a card that asks for a pick (its options, or a row's) and names none (`pick`), since there is nothing for an approval to take. Until November 12, 2026 an approve was refused on any card with a pick or a row marked `own_yes`; that day the approver asked for those to be the deputy's to judge as well. The why is required, under 300 characters, and written for the approver.
- **In a dry run,** and for `--his` in either mode, the call is recorded and the card, still waiting on him, gets one gray line above its footer, redrawn in place with no notification: "🤖 Dry run · <name> would have approved this for you: <why>" or "🤖 <name> left this for you: <why>". The asker hears nothing.
- **With auto-approval on,** `--approve` approves the whole card for the approver through `core.decide` (every open row of a set, a row marked `own_yes` included, and every item of a batch; only the approver's own Approve all still skips `own_yes` rows), with the decision marked as the deputy's (`where: "deputy"`, `by` its name, and its `why`). The asker gets the usual decision message, paced and acknowledged like any yes, saying it was approved for him by his deputy, why, and to act on it as on his yes for exactly what the card describes, since he has not seen it (to him it is "your deputy approved it", never "you approved"); `done` works after it. Where the card asks for a pick, the approve takes the pick the card names: at the card's level the decision carries it as `choice`, and a row with options is answered `chose` with that row's pick, by the deputy. The asker's message then says which pick was taken and to do exactly what the card describes for it; the answered card's timeline reads "🤖 Approved for you by <name>, taking the card's pick, <pick>", each row the deputy answered reads "for you by <name>", a dry run's gray line names the pick it would take, and the morning summary's line adds "took the card's pick, <pick>". The reviewer, for its types, is told as for any decision. The card collapses as an answered one does, headed "🤖 Auto-approved: <title>" (until the agent sets a headline), with "🤖 Approved for you by <name>, <time>: <why>" first in its timeline; the morning list crosses it off as auto-approved.
- **Take it back** sits beside See the card on an auto-approved card, for the approver only, at any time, done included. It records `taken_back`, makes the card's decision his decline (`where: "took back the auto-approval"`; a set's rows the deputy approved show as declined), and tells the asker to acknowledge, stop, undo what it can and say on the card where it stands, and tells the deputy. That message isn't paced like a decision: it takes a yes back, so like a reply in the thread it goes at once, typed right behind the yes if the yes hadn't gone yet. The card then reads "↩️ You took it back: <title>" and "↩️ Auto-approval taken back by <approver>, <time>. <name> had approved it: <why>", then the agent's status lines.
- **The morning summary.** Right after the 8 am list (not a list asked for), when there's a deputy and it made a call since 8 am yesterday, one more message in the channel, with no mention. It's a snapshot rendered from the records and not kept current. With auto-approval on, it counts the cards approved for him, how many he took back, how many it left for him and how many of those he approved without a word, then lists every auto-approved card grouped by asking agent, a taken-back one struck through. In a dry run, it counts the cards it would have approved out of the cards it called, and for each says what he did instead: approved without a word, replied, declined (or removed), still open, withdrawn, or closed with no answer. "Approved without a word" is `core.plain_yes`: his first decision on that version was Approve by the button (a whole batch ticked in Pick which counts; edited words, a partial batch, a pick or words recorded from elsewhere don't), with no reply of his before it; nothing acts on it but these counts. Lines are packed into sections under Slack's 3,000 characters, the whole message under its 50 blocks, the rest counted in "…and N more". Its one button, Pause auto-approval or Turn auto-approval on (`deputy|0|pause`, `deputy|0|live`, handled before any record is looked up, the approver only), switches the mode at once and redraws the summary with the other button and who switched it when.
- **Reading the record.** `approvals history` prints cards newest first, by asker, type, age or only those the deputy called, each with what happened in order: the deputy's call and why, the approver's replies quoted, his decision and how long after the version was posted, a withdrawal and its reason. Only facts from the records, with no ranking. It is filtered where the records are kept (`/history` on the hub), so the deputy's many looks at a few cards never bring every record across the network. `approvals pictures <id>` saves the newest version's pictures, as the card uploaded them to Slack, into a folder and prints their paths, and prints any video's link, so a session can look at what the approver would see.

### A card shared with the approver's team

On a card for the default approver, `call --his --also <name>` saves the name on the call and records a send in `also` with the version, display name, Slack user, why, call time and any scheduled delivery time. A teammate's quiet hours hold both deputy sends and hand-offs until the end of the quiet hours on their next working day, in their zone, while `--urgent` on a deputy send makes it due on the next sweep and explains the override in the direct message if the call would have been held. A call that names a teammate stands in dry run too. The hub's sweep sends only if the version still waits on its first answer. It saves the direct message's channel, timestamp and send time, or marks the send skipped if the card has moved on. Slack failures are tried in the next sweep.

The DM shows the full open card and the deputy's reason for sending it, with **Not mine** and a link to the channel card. The card in the channel stays available throughout. Sent DMs redraw with the record, including when replaced or handed back. The listener accepts the sent teammate's buttons, pop-ups and replies for the current version. It reads the DM thread on its normal polling schedule and quotes those replies in the card's channel thread. Only the recipient can use **Not mine**, which tells the deputy and ends the recipient's access when `team_answers_any` is off. Remove, Take it back, Back to me, Hand to and the deputy switch remain the approver's.

Teammate answers carry the Slack user in their events and use the name stored on the send for messages, cards and history. With `team_answers_any` on, answers without a send use the teammate's configured `name` or the default approver's `approver_name`. The morning summary includes sends since yesterday morning when auto-approval is on and counts only the approver's own plain yeses.

**Hand to** on the channel card or list makes a new current send. It closes the previous send for that version and redraws its direct message with the new person's name. The hand-off saves who handed it over and when, and the return time. The clock starts at scheduled delivery and counts only time inside the recipient's work window on their days, in their zone. A teammate's hours are the pod dashboard record's (`days`, `from`, `to`, `zone`, read with the team): work is from to to, quiet is to to from; a hub that keeps its team in its own settings gives `quiet` and `work` there, on weekdays in the workspace time zone. The card's deadline is at least its usual window after the return time. The asker gets one message naming the person and new deadline, and the deputy hears who is holding the card.

The channel card shows who has it, with **Back to me** and **See the card**. With `team_answers_any` on, it displays the full card and its answer buttons beside **Back to me**. The list counts only cards waiting on the approver and shows hand-offs under **With your team**, with the same answer buttons. Once the return time has passed on a delivered send still awaiting its first answer, the hub marks it returned, tells the deputy and mentions the approver in the card's thread. A row answer that leaves other rows open keeps the card with the teammate. A reply followed by the agent's answer on the same version reopens the card with the teammate. In both cases the channel card and list show when the teammate responded, and the direct message drops the return time. The teammate can still answer after an automatic return or **Back to me**. **Not mine** also mentions the approver in the thread.

A revision carries an unreturned hand-off to the same person with fresh delivery and return times. A deputy call with `--his` leaves the hand-off in place, and `--also` is refused if the version already has a send. The summary shows the return time for hand-offs awaiting a first answer and records replies, answers and automatic returns. The history shows hand-offs, automatic returns and **Back to me**.

Once the current send is delivered on an open card, a hand-off or a teammate's response makes the DM thread part of the conversation. The listener quotes the approver's typed replies and pop-up words in that thread, and `answer`, `ack` and `ask` use the same text, blocks and sender in both threads.

## Acknowledgements

📨 means one thing: the service saw its message in the agent's transcript. That proves delivery, not understanding.

**The agent's acknowledgement:**
- A decision (a yes, a no, a pick, items) tells the agent to acknowledge first with `approvals ack`, in its own words: what it understood and what it's doing now. For example: "Got it: you approved v2. Posting the reply now, then I'll mark it done."
- A reply or a question in the thread doesn't: the agent's answer (`approvals answer`, or `approvals revise --answer` when the answer changes the card) or its next version is the acknowledgement, so the approver meets the answer first and no "Got it, I'm checking" post (November 10, 2026: "Please stop sending me the same approvals and just ... talk to me"). Every post of the agent's on the card counts: an answer, a new version, a status line, a question, a withdrawal, done. A separate `ack` is only for a reply that will take more than a few minutes, saying what's coming and when.
- `approvals answer` posts the answer with its first sentence in bold and the agent's name in the small line under it. On a card waiting on the agent after a reply, it reopens the same version as pending. An active hand-off stays with the teammate. Other reopened cards count on the approver's list again. On an approved or withdrawn card it posts and changes nothing else.
- Deadlines need no acknowledgement.
- An acknowledgement covers every answer on the card that has gone to the agent (typed in, or read from its inbox), not one still waiting its turn. Answers are counted as gone the moment typing starts, since agents often acknowledge before their transcript shows the message.
- The thread then shows, from the agent itself, what will happen. Any later difference between the acknowledgement and the action is visible there.

**The warning.** A delivered answer that hasn't been acknowledged after 10 minutes gets one ⚠️ note in the thread. It names the agent and says nothing confirms the answer was understood or acted on.

**Asking again.** A reply (feedback, an answer to its question, a comment after the decision, typed in Slack or on the pod dashboard) that the agent hasn't acknowledged is typed in again 10 minutes after it landed, then every 30 minutes, as a message of its own (`again`, no acknowledgement of its own, no 📨) that quotes what was sent and when it landed. The reply's outbox entry keeps each time in `asked_again`, which the dashboard shows. It stops when the agent posts on the card (any post acknowledges everything sent, `approvals record` included) or the card is withdrawn or done. A reply waiting for an agent that isn't running was never delivered, so it is never asked again: it waits for the agent. The thread's ⚠️ note stays one. Where the pod dashboard's record keeps the cards, the hub asks nothing again: the record asks the asker by the rule it holds for every person's line, until the asker posts a line of its own on the card, whether the card was withdrawn, done, declined or revised, and types a reply this hub held for a session that isn't running into the asker by its name (pod-dashboard `db/parts/92_card_lines.md`; AP-2245, whose note of November 22 waited 14 hours).

## Polling and deadlines

- **Replies:** Slack message events from approvers and workspace teammates flag threads in approvals channels for the next polling round. Open DM threads are due every 15 seconds and go ahead of the rotation within the same read budget. The hub hands a reply to its own sessions within 5 seconds, and the other machines ask for theirs every 5 seconds.
- **The safety net:** the listener also reads every watched thread in turn (any card with activity in the last 14 days), 3 every 5 seconds. With hundreds of cards a full pass takes about 15 minutes, so this only catches replies Slack didn't flag, such as while the connection is down.
- **Deadlines:** at its deadline a request is marked "No answer: not approved" and the agent is told. A reply after that reopens it.

## The morning list

Cards arrive all day and night, and a card nobody answers closes as a no, so its agent drops it. The morning list keeps one place that says what still waits on the approver.

- **When:** at 8:00 am in the workspace's `timezone`, the listener posts one message in each approver's channel, mentioning that approver. A service that was down at 8 posts when it comes back that day. `digest.json` in the workspace's folder keeps the default approver's newest list; each named approver has a separate `digest-<name>.json` state file. Existing default state stays in place.
- **On demand:** any post of the channel's approver in that channel, outside a card's thread, asks for their fresh list. The channel holds only cards, so nothing else is posted there that way. Every 5 seconds the listener reads each channel's posts since its newest list and, if one asks, posts a new list at the bottom, without the mention. An ask before 8 am doesn't replace the morning list.
- **What's on it:** only that approver's cards waiting on their answer: new cards, new versions, and agents' questions (status `pending` or `question`). Cards waiting on their agent (revising after a reply, or acting on a yes) stay off, and so do cards waiting on someone else (`approvals status --waiting-on`, until a later line) and TEST cards. An approved card is on it only while its newest line says it waits on him (`--on-you`) and he hasn't answered since: a card waits on one party at a time, so a `--waiting-on` line replaces an earlier `--on-you` and the other way round, and his answer after an `--on-you` line is what it waited for. Without that, approved cards stayed on his list for a line their agent had posted before his yes.
- **One tap from the list:** each card waiting on the approver's answer has an actions row under its line: Approve, Deny and Remove. Each sends the same button value the card's own buttons do (`<id>|<version>|approve`, `decline`, `all` for a set's plain rows when two or more are open, `pick:<i>` for each option of a choice not shown in pictures; every other open row of a set, one marked `own_yes`, one with options, or the one plain row left, gets its own buttons, `p<j>:approve` or `p<j>:pick:<i>`, named for its row when the line has several, since a release card, whose rows all need their own yes, otherwise showed only Deny and Remove; Slack's 25 buttons a row cut the rest, which stay on the card), so the hub handles it exactly as a press on the card. Remove (`remove`) is the one new answer: the card is saved as withdrawn with `withdrawn.by` set to the approver, its card shows "Removed", and its agent gets a message to acknowledge, saying nothing on it is approved and that a removal is no verdict on the idea. A card waiting on him for a condition after his yes (`--on-you`) has no buttons. After any press the hub redraws the list at once, rather than at the next sweep, under a lock the sweep shares.
- **Slack's 50 blocks:** a waiting line is three blocks (the card, its gray line, its buttons), an answered one two. Lines are added in order until the next would pass the limit; the rest are counted in a last line asking for a fresh list once some are answered.
- **Order:** grouped by the day the card closes (today, tomorrow, later), soonest first. Each line links the request number to the card's first post, which always shows the newest version, and says the agent, when the card last came to the approver, and when it closes.
- **Closed with no answer:** cards that hit their deadline since the last list get their own section. A reply in a closed card's thread reopens it, and nothing new is posted in the channel when a card closes, so this is where the approver learns of it.
- **Kept current:** every 5 seconds, the listener renders the newest list again from the records and edits the message when anything changed. A card that stops waiting on the approver is struck through with what happened: approved, declined, replied to, withdrawn, or closed with no answer. A card that comes back with a new version is shown as waiting again. Cards that arrive after the list is posted are left to the next list.
- **One list at a time:** when a new list is posted, the one it replaces is edited down to a link to the new one, so the channel never shows two lists that disagree.
- **Nothing waiting:** one line saying so, mentioning no one.
- **Failures:** the record of today's list changes only after Slack accepts the post or edit, so a failed one is tried again on the next sweep.
- **The deputy's summary** follows only the default approver's morning list when there's a deputy that made a call (above, under The deputy). It's posted once; a failed post is logged and not tried again.
